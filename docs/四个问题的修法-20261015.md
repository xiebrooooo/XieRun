# 四个老问题的根因与修法（2026-10-15）

本轮改的是主项目里长期存在的四件事：**打卡点拉不起来 / 批量天数乱 / 预览与提交不一致 / 轨迹断断续续**。
每条都尽量做到「有样本、可复现、有回归测试」，证据来源在第一节写清楚。

## 二、问题 1：有些学校的打卡点拉不起来

### 旧行为

[points.rs](../src/api/points.rs) 把点位路径写死成 `/api/v560/get/1/distance/1`，body 里 `sportType=4`，
不传学校区域 id，围栏响应里的 `passPoints`（必经打卡点）根本没解析。
候选只有一个：这个请求返回空，整条跑步链就在第 ② 步直接失败（`实时点位为空 —— 拒绝本地样本兜底`）。

### 为什么会「有些学校」不行

| 线索 | 说明 |
| --- | --- |
| 参考实现用的是 `v560/get/{sportType}/distance/{distance_m}` | 路径末段是**目标距离（米）**，不是固定 `1`；按距离出点的学校只有带真实距离才有点位 |
| 端点表里同族端点有三条：`v560/get`、`v560/get/1/distance`、`v560/get/destinationRun/points` | 目的地跑是另一套点位，写死单一路径必然漏 |
| 参考套件从 `geoFences[].passPoints[]` 取必经点 | 有的学校点位只在围栏响应里下发，点位接口本来就是空的 |
| 多区域校区要带 `runAreaId` | 学校配置了多个跑步区域时，不传区域可能拿到空集 |

### 改法

1. **候选端点轮试**（[points.rs](../src/api/points.rs) 的 `candidates()`）：旧请求放第一位（已跑通的学校行为不变），
   后面依次是「真实目标距离」「距离 1」「基路径」「目的地跑」；命中非空即返回并打印是哪条端点拿到的。
2. **围栏必经点兜底**：新增 `fence::fetch_geo_fence_points()`，把 `geoFences[].passPoints[]` 解析成点位对象
   （BD 优先、GCJ 回退，坐标去重），点位接口全空时改用它。
3. **`runAreaId`**：`policy` 响应里防御式提取（`runAreaId` / `areaId` / `zoneId` / `runArea` / `zone`），
   有就带上、没有就不传（与 App 行为一致）。字段名未经验证，只做「有则带、无则不带」。
4. **缓存点归一化**：命中缓存时也补全 BD/GCJ 双系字段（旧缓存可能只存了一种坐标系）。
5. **只读探测命令**：`probe points|fence|policy|zones|gmttime|ai`（见第六节），
   出问题时不消耗跑步配额，直接把每个候选端点的真实返回打出来。

### 怎么验证哪一步生效

```powershell
# 换到出问题的那所学校账号后执行：逐个候选端点都会打印返回
.\nekosportsworldtool.exe probe points --dist 2000
.\nekosportsworldtool.exe probe fence      # 看 passPoints 有没有下发
.\nekosportsworldtool.exe probe zones      # 看校区区域列表长什么样
```

### 线上实测（2026-10-15，天津某校账号）

`probe points --dist 2000` 的真实返回：

| 请求 | 结果 |
| --- | --- |
| `/api/v560/get/1/distance/1`（body sportType=4） | 5 个点（操场1–5），**isFixed=1** |
| `/api/v560/get/1/distance/2000`（body sportType=1） | 同样 5 个点，**isFixed=0** |
| `/api/v560/get/1/distance/1`（body sportType=1） | 同样 5 个点，isFixed=0 |
| `/api/v560/get` | HTTP 404（该路径当前不可用） |
| `/api/v560/get/destinationRun/points` | HTTP 404 |

两条结论：

1. **点位接口有 5 分钟 3 次的限流**：第 4 次开始返回 `error=10603 您在前5分钟内获取点位已达到3次`。
   所以多候选回退必须限量，否则一次失败的运行会把配额烧光、下一次也起不来。已做：
   - 运行期只试前 3 个候选（`MAX_CANDIDATES_PER_RUN`）；
   - 一旦看到 `10603` **立即停止**换端点（换哪个都被拒），直接走围栏兜底/缓存；
   - 缓存 TTL 300s 不变，命中缓存不发请求。
2. `sportType` 会改变 `isFixed` 标记，两个变体都要保留；
   `/api/v560/get` 与目的地跑路径当前 404，因此降级到最后（`probe` 仍可单独试，不占运行期配额）。

> 现在这套回退对「原本能跑通的学校」是零改动的（第一条候选与旧版完全一致、且优先）；
> 只有第一条返回空/报错时，才会去试第二、第三条。

## 三、问题 2：批量补签的天数跟要求对不上

### 旧行为

`run_ai_batch` 每轮只知道「提交成功了几条」，**从不回读服务端**；
今天的记录用 `now - timeConsume` 当 `scoreDate`，过去的天用当天 7:00–21:00 随机；
一旦服务端丢单、改期或限额，用户看到的就是「要求 30 天，实际天数乱掉」，且无从知道差在哪天。

### 改法（[ui/ai.rs](../src/ui/ai.rs) + [api/ai.rs](../src/api/ai.rs)）

1. **按天生成确定清单**：天数 = 用户填的「补签天数（含今天）」，先为「每天每条」抽好时刻，
   重试沿用**同一个时刻**，不会再因为重试把记录挪到别的日子。
2. **不生成未来时刻**：今天用 `[今天 7:00, 现在]`（早于 7:00 则退化为 `[0 点, 现在]`）；
   `api/ai.rs` 里再兜一层 `scoreDate = min(传入, now - timeConsume)`，杜绝跨天。
3. **提交后按「天 × 项目」回读核对**：拉 `v66/sport/ai/record/infos`，用 `scoreDate` 折算回「距今天几天」，
   统计每天每项目实际落库条数。
4. **缺的自动补投一轮**，仍然用当天抽好的时刻。
5. **按天报结果**：弹窗与日志逐天显示「提交 x · 服务端 y / 要求 z」，天数对不上时一眼看出是哪天。
6. 回归测试：`ui::ai::tests`（时刻必须落在目标那一天、绝不在未来、回读时间戳折算天数）。

> 注意：这一版解决的是「客户端不知道差在哪、且被动接受服务器丢单」；**如果服务端硬性限制补签天数**
> （例如只允许近 7 天），回读核对会如实报出来 —— 那就属于规则限制，不是客户端能绕的。

## 四、问题 3：路线预览和实际提交不一样

### 根因（一共有四处，只修一处都还会不一致）

| # | 位置 | 旧行为 |
| --- | --- | --- |
| 1 | [generate_road.rs](../src/track/generate_road.rs) | 预览用 `RouteOptions::default()`（转弯半径 6m），提交用 `v²/a_c` 算的半径 → **同一种子算出两条不同路线** |
| 2 | 同上 | 预览的函数签名里根本没有「时长」，提交侧却在提交前把时长按配速窗口改过（`fit_duration`）→ 半径跟着变 |
| 3 | [flow.rs](../src/api/flow.rs) | 提交时重新联网拉围栏，预览用的是围栏缓存 → 两次围栏集合不同，路线跟着变 |
| 4 | [ui/run.rs](../src/ui/run.rs) | 「经典打卡点环」模式**没有预览**，切过去是一片空白；用户只能提交完才看到轨迹 |

### 改法

1. `route_options(dist, dur)` + `plan_route_for_run(...)`：预览与提交**共用同一个规划入口**，
   输入相同 ⇒ 路线逐点相同。
2. `plan_road_view(net, points, dist, dur, seed, fences)` 增加 `dur` 形参；
   时长钳制上移到 `generator::fit_duration`，UI 抽样时就用同一个值（`flow.rs` 仍保留兜底调用）。
3. 提交时**优先复用新鲜围栏缓存**（`fences_for_submit`，24h 内直接复用，含「空围栏」这个有效结果），
   预览用的哪份围栏，提交就用哪份。
4. 经典模式补上本地预览：`draw_run_map` 现在两种模式共用一套绘制（路线/打卡点/起终点），
   经典模式直接本地跑一遍生成器，画的就是要提交的那条轨迹。

### 回归测试

`track::tests::test_road_preview_matches_submission`：同参数下提交轨迹的每个点都必须落在预览路线上（<12m，差的是 GPS 抖动），
并把时长拉大 4 倍验证「转弯半径确实参与规划」。旧代码在这条测试上偏差 1000m 级。

## 五、问题 4：轨迹断断续续、不像真人

### 根因

丢星点（`type=-1`）在旧实现里是「**按随机方向甩 2–300 米**」（`generator.rs` 与 `generate_road.rs` 各一份）：

```text
lt=4 → 32% 概率 2–60m（5% 概率 60–250m）
lt=12 → 必然 5–80m（10% 概率 80–220m）
lt=5 → 5–60m      lt=6 → 100–300m
方向：ang = uniform(0, 2π)   ← 随机方向
```

真人样本给出的答案完全不同：**42% 原地复制上一点坐标，50% 在 0.6–20m，8% 在 20–50m，没有 >50m**。
随机方向的大位移在图上就是一串「断崖 + 回折」，这正是用户看到的断断续续。

### 改法

新增 `geom::lost_fix_offset()`：丢星点改由 **AR(1) 相关漂移**决定位移（同一方向连续几帧、幅度缓慢变化），
并硬性限制在 50m 内；45% 的概率直接原地复制上一点坐标。两个生成器（经典 / 真实道路）共用这一个函数。

### 验证（可复现）

```powershell
# 本地生成样本（不联网、不上传），直接打印与真人基线的对比
.\nekosportsworldtool.exe track-sample --dist 2100 --dur 700 --seed 7 --route legacy `
    --points "NekoSportsWorldTool-个人免卡版-20261008\dist\个人免卡版-天津-20261012-v9\points_cache.json" `
    --out _pytmp\ours_legacy.json
.\nekosportsworldtool.exe track-sample --dist 2100 --dur 700 --seed 7 --route road `
    --points "...\points_cache.json" --net "tools\road-network\辽源职业技术学院.osm" `
    --out _pytmp\ours_road.json
python tools\track-check\track_stats.py "_pytmp\ours_legacy.json" "_pytmp\ours_road.json" history_tracks\*.json
```

修复后的实测（与真人基线同表对比）：

| 轨迹 | 点数 | 间距中位 | 间距 99 分位 | 间距最大 | 丢星点 | 其中原地 | 丢星位移最大 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ours_legacy | 145 | 15.0m | 29.0m | **29.8m** | 5 | 2 | **13.9m** |
| ours_road | 144 | 15.4m | 29.8m | **38.1m** | 3 | 0 | **24.7m** |
| 真人 10 条 | 198–840 | 6–12m | ≤37m | ≤48m | 0–7 | 42% | 47.9m |

回归测试：`test_tracks_are_continuous_like_real_samples`（最大间距 ≤60m、99 分位 ≤55m）、
`test_lost_fix_points_match_real_samples`（丢星位移 ≤50m、原地比例 ≥25%）。

## 六、新增的两个命令

```text
track-sample [--dist m] [--dur s] [--seed n] [--route legacy|road]
             [--points <点位json>] [--net <osm>] [--out <file>]
             本地生成一条轨迹样本并打印间距/丢星点分布（不联网、不上传）

probe <points|fence|policy|zones|gmttime|ai> [--dist m] [--sport n] [--area id]
             只读探测：打印该协议域的真实响应；
             points 会逐个候选端点试探，用来定位「哪所学校为什么拉不到点位」
```

两者都不需要额外登录：程序用 exe 同目录里已保存的账号与会话（`accounts.json` + `session.json`，
没有会话时按记住的密码自动重登一次）。**注意先把新 exe 放到平时那个程序目录再跑**，
换目录执行等于换设备身份（`identity.json`），可能触发 10121 设备风险。

## 七、还没做 / 待真机确认（诚实记录）

1. **`runAreaId` 的真实来源**：现在只从 policy 响应里防御式提取。
   如果某些学校必须带区域 id，`probe zones` 的输出能直接告诉我们字段名，再改成主动获取。
2. **AI 记录服务端是否限制补签天数**：回读核对会把真实情况报出来，但要改「能不能补」得看规则。
3. **点位候选的优先级**：第一条仍与旧版完全一致（先保住已跑通的学校），
   若确认「按距离出点」才是正解，把 `candidates()` 的前两项互换即可，其余不用动。
4. **路线闭环长度 ≈ 目标距离**：规划器给出的是闭环，长度与目标距离本就允许有偏差，
   提交轨迹按目标距离截取；这一点与真人记录一致（真人也常常不是标准闭环）。
