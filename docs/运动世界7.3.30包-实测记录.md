### 修正：是"字符串明文 + 结构加密"的分节加固，不是全明文

`classes.dex` 的**头部**写着 `class_defs=30 / string_ids=1097 / data_size=50 KB`，而文件本体 77.8 MB —— 也就是说这个 dex 只是**壳存根**（30 个网易易盾 wrapper 类），真 dex 在同一个文件里被加密。查证：

| 证据 | 结果 |
| --- | --- |
| `classes.dex` 头（apkpure 7.3.30） | file_size=77838064，class_defs=**30**，string_ids=1097，data_size=50832 |
| `classes.dex` 头（用户给的 7.3.21） | file_size=85015028，class_defs=**30**，string_ids=1099，data_size=50872 |
| androguard `DEX.get_classes()` | 只返回 30 个类，全是 `com/netease/nis/wrapper/*`、`La/auu/a;`（易盾壳） |
| 全包扫描 `dex\n035\0` magic | 只有 offset 0 那个存根，**没有内嵌的明文真 dex**（`carve_dex.py`） |
| 但字符串池是明文 | 78522 个类描述符、2797 条 `api/...`、字段名都能直接 grep 到 |

**所以能力边界是这样的**：

| 能拿到（免脱壳） | 拿不到（需运行时 dump） |
| --- | --- |
| 类名清单（app 自研 6403 个） | 类成员（字段声明顺序/类型、方法签名） |
| 全部端点路径（216 条，已导出） | 方法体、常量默认值（`maxRunTime`/`minSteps`/`status`） |
| 字符串常量（端点的、部分字段名） | 风控判定逻辑（`PointCheckStrategy` 等） |

要拿右列，只有运行时 dump（Frida dex dump / youpk 之类）一条路；爱加密 + 易盾双层的纯静态还原不划算。

## 三、风控面

**环境检测主要来自第三方 SDK，不是自研**：网易易盾（`libnesec.so`，含 x86 变体）、爱加密（`libijiami_1011.so` + `assets/ijiami_1011.VData`）、`libzxprotect.so`、小米 zeus safe SDK、Bugly/友盟上报。

app 自研里与"被检测/位置可信度"直接相关的类：

| 类 | 含义 |
| --- | --- |
| `utils/DebugHooks$hookLocation` / `hookTelephony` | **官方自留的 hook 入口**：位置与电话信息可被注入，说明风控并不只看本地定位 |
| `entity/sport/HookVirtualBean` | Hook / 虚拟环境相关实体 |
| `utils/sport/plugin/PointCheckStrategy`、`PluginableLocationManager`、`LocationManagerRegistry` | 可插拔定位管理器 + 点位校验策略（打卡点判定的本地侧实现） |

| `service/RunLocationService`、`BaseLocationManager` | 跑步定位服务 |
| `utils/rundata/RunSportUploadManger$addFaceCheckDataAndUpload`、`RunFaceCheckDatabase`、`baiduFace/*` | 人脸打卡（faceCheck）完整链路 |
| `mvi/sport/CreditRunPIml`、`RunFreePImpl`、`RunStartViewModel` | 计分跑 / 自由跑 / 开跑向导（提交报文的拼装处） |

## 四、还没答上的（诚实记录）

算法常量在 7.3.30 包里**明文找不到**：请求公钥尾串（`uZ3o1YtkAyGzjaJnw`）、盐（`2slhe`/`sls-_slaor`）、iOS 侧 keyData 常量（`nhang.school`）全部未命中 dex 与任何 so → 要么被加固/易盾的字符串加密保护，要么在 native/Dart 里运行时拼装。

所以"算法有没有变"这条**静态答不了**，只能靠：① 抓包交叉验证（已做：公钥与 KDF 与本地实现逐字节一致），② Frida hook `libnetseckit-4.2.4.so`（未做，收益低）。

## 四、动态分析对抗记录（真机：OnePlus PLK110 / Android 15 / KernelSU root）

在真机上对 7.3.93（versionCode 407，小米应用商店安装）做脱壳尝试，结论是**这个包对动态分析有主动对抗**：

| 手段 | 观察到的现象 |
| --- | --- |
| frida attach（`frida-dexdump -F` / spawn `-f`） | 主进程在 frida 进程列表里**不可见**（只看到 `:pushservice`），attach 报 `unexpectedly timed out while waiting for stop`，随后主进程消失 |
| lock screen 干扰 | 排除：解锁后 frida 仍看不到主进程 |
| `pidof` 查 pid | 返回空，但 `ps -A` 能看到进程 → 壳改了 `/proc/<pid>/stat` 的 comm（必须用 ps 解析 pid） |
| root 读 `/proc/<pid>/mem` | **可以读**（SELinux Enforcing 下也成功，单区间 dd 返回 rc=0 与真实数据） |
| 批量读内存 | 读到第 2 个区间时进程死亡（`read: No such process`），壳有"被读取即自杀"的看门狗 |
| 启动期进程 | 壳会在启动后重新 exec（pid 多次变化），maps 抓下来就过期，必须"同一个脚本内解析 pid + 读 maps + dump" |
| 清数据 / 恢复 SELinux | 都不能恢复"能 attach 的状态"，说明是环境态检测而非持久标记 |

**可复用的结论**：脱壳要么换更抗检测的 dumper（BlackDex 等），要么换设备（模拟器对加固常降级处理），要么改走抓包路线；在真机上硬打 frida 的性价比最低。

### 模拟器（MuMu 12）复测结果

| 项 | 结果 |
| --- | --- |
| root | `adb root` 直接可用（不需要动 MuMu 设置里的 ROOT 开关），`id` = uid=0 |
| App 进程 ABI | **x86_64**（`/system/lib64` 映射 1082 个，arm64 路径 0 个；只有 ARM 原生库走翻译） |
| x86_64 frida-server | ✅ 能起来（非默认端口 23456），`frida-ps` 能列进程 |
| 主进程可见性 | ❌ 只在列表里看到 `:pushservice`，主进程不可见（与真机一致） |
| 按 pid attach | ❌ `unable to write to process memory: No such process`，随后 `am_proc_died [2825]` —— **attach 即自杀** |
| root 内存 dump | ✅ 589 个区间读成功 160 个 / 367 MB，进程全程存活；另做了一轮 app 目录定向 dump 259 MB |
| 内存里有无明文 DEX | ❌ 扫遍 600+ 区间**没有有效 DEX 头**（只有 3 处假魔数，头部字段为 0）→ 该壳疑似**按页按需解密**，完整明文 dex 从不驻留 |
