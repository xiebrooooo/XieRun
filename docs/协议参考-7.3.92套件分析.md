## 一、这是什么

仓库 `Inverx/com.zjwh.android_wh_physicalfitness` 的 `协议/` 目录下有两个版本：

| 目录 | 形态 | 文件数 | 说明 |
| --- | --- | --- | --- |
| `协议/7.3.40  /`（目录名带两个尾空格） | 单层脚本 | 17 | 旧版，`netsec_crypto.py` + `running_protocol.py` + 各 `*_cli.py`，有响应验签 |

7.3.92 自述信息（`README.md`）：

- 版本 `7.3.92`，`versionCode 406`
- 抓包来源：`xadsmartget.adgain.cn_2026_10_14_23_26_10.har`（登录-跑步）、`s.adxvip.com_2026_10_15_09_42_15.har`（已登录开跑）
- 自研"NetSecKit 4.2.4"纯标准库实现（AES-128-CBC + Feistel KDF + RSA PKCS#1 v1.5）

即：**别人对 7.3.92 抓包后写的 Python 协议客户端**，不是官方 SDK，也不是反编译产物。

## 四、与本地 Rust 实现逐项对照

### 4.1 加密层：两套形态，都合法，不要改

| 项 | 7.3.92 参考（Android 形态） | 本地 Rust（iOS 形态） | 判定 |
| --- | --- | --- | --- |
| `platform` | `2` | `1` | 服务端只回显 keyData，无所谓 |
| keyData | `uuid4().hex + "ABCDEFGHIJKLMN12"` 切 4×10 字符 | `nhang.school` / `5K0E8400-E29` / `597DEA1AFB49` + 毫秒 `%f` 末 12 字符（会话内缓存） | 都满足 KDF 的 8–12B 约束，KDF 已验证同源 |
| inner 键序 | 字母序（data/keyDataFour/One/Three/Two/platform/timeStamp） | 固定序（data,timeStamp,platform,keyDataOne..Four） | `h` 各自算各自的，服务端只解 `data` |
| inner `timeStamp` | **秒** | **毫秒** | 差异，两边都能过 |
| reqKey | 小写+数字 36 池 | native 白名单 64 字符池 | 随机会话密钥，无影响 |
| 响应验签 | **完全不校验 `s`** | RSA 恢复 MD5 比对，fail-closed | 本地更强 |

顺带一个有意思的点：7.3.40 版参考用的是"4 段随机 8–12 字符 + 94 个可打印 ASCII 池"，7.3.92 版换成"uuid 派生 4×10 + 36 池"——**这是换了抓包设备/平台，不是协议变更**，因为两版 KDF 完全一样。

## 五、建议采纳清单（按性价比排序）

### P0 低风险、可立即做

1. **补服务端时间对齐**：`GET /api/v3/getserver/gmttime`，跑前取一次、提交前再取一次，用服务端时间推 `stopTime/startTime`（失败回退本地时钟）。参考套件明确写了"二次对齐"这个真机时序，本地目前完全没有这一步（`src/api/client.rs` 加 helper，`flow.rs` ③ 前调用）。
2. **`get_one_record` 版本回退**：先试 `/api/v70320/runnings/get_one_record`，非 10000 再回退 `/api/v70260/...`（`records.rs` 一处改动，验证方式：随便查一条历史 rrid 比对字段是否一致）。
3. **OBS 对象补 `extension_json`**：`wire.rs:build_obs_object` 加 `"extension_json": gz_str("")`，前提是先用现成 `obs::fetch_object` 回读一条真记录确认服务端对象里确实有这键（有则加，没有则别加）。

### P1 需要真机样本复核

4. 提交 body 逐字段比对第 4.3 节的冲突项，用一条真实记录 + 一次提交前后对比来定论。
5. **埋点链**（`startup/pv` + `datacollection/pv`）做成**默认关闭的开关**：它的载荷字段（`itemId="My_page_exposure"`、`module=10018` 等）看起来是拼出来的，伪造埋点本身也是风控特征；没有抓包复核前不要默认发。
6. 需要"数据中心/日历/详情页"功能时，照 4.2 的新端点清单实现（`v70390/user/info`、`v77/home/page`、`v70340/activity/rundetail/config`、`v74` 室内分页、`v70100/run/calendar/list`）。

### P2 只做研究/诊断

7. `v1/barrierFree/getBarrierFree`、`v78/cheat/cheatlist`、`creditscore/v70390/popup`、`control.gxapp.iydsj.com/getMessage` —— 这四个是**风控自观测**入口，出 `10121`/`10603` 时用来判断命中了哪条规则，比盲调参数有用。
8. 广告与室内跑（`v68`/`v59`）链，等真要做对应功能再说。

### 明确不要采纳

- ❌ 不要改成 Android 形态信封（`platform=2` + uuid keyData）。KDF/AES 已证明同源，本地 iOS 形态线上验证过，切换零收益纯风险。
- ❌ 不要按参考套件去掉响应验签（本地 fail-closed 是强项）。
- ❌ 不要照抄它的轨迹/分桶算法（±0.00003° 均匀抖动、步频/速度桶平均分配）。本地 `wire.rs` 的 10s 桶 id 由 `rrid` 派生，有真人样本依据，别退化。
- ❌ 不要用它当"7.3.92 新协议"的证据去大改版本号：请求公钥、盐、结算端点全部没变，只有 `appVersion` 字符串不同。

## 九、可学习点（工程手法层面）

实现层一条都不值得抄（见第六节），但下面 5 条手法值得学，按性价比排序。

### 1. 每个域一个"只读探测入口"

参考套件每个模块都配了 `cli.py`（`-u/-p/-t --rules/--profile/--history/--run`），可以**单独跑一个协议域**而不触发全链。我们的 CLI 已经有很多子命令（见 [cli/mod.rs:19](../src/cli/mod.rs#L19) 的 `usage()`），但缺一类：**不带副作用的探测命令**——想确认"policy 现在返回什么""电子围栏有没有更新""这条 rrid 的 reasonList 是什么"，现在只能开 GUI 跑全链（会真的产生一条记录）。

落地：加 `probe <域>`（`policy|fence|points|gmttime|record --rrid N|observe`），全部只读、`silent()` 日志换成打印 JSON。这是本次最值得抄的一条，收益是排障时不再消耗跑步配额。

### 2. 把真机时序写成文档，而不是只写在代码注释里

参考套件 README 里那节"真实全链路业务时序与防风控规约"记录了一条**抓包字段之外**的信息：跑步进行中客户端不发任何 HTTP（GPS 离线采样），跑前跑后各对齐一次服务端时间。这类"时序事实"是判断"我们哪一步顺序不对"的唯一依据。

我们的对应知识散在 [flow.rs](../src/api/flow.rs) 的注释里（比如"先结算后 OBS"）。落地：docs 加一页真机时序规约（policy → 点位 → 静默期 → OBS → 结算 → 回查 → 首页回刷），把我们与真机不一致的两处显式标出来（OBS/结算顺序、缺时间对齐）。

### 3. 契约先行：响应先落模型，再写解析

参考套件每个域都有 `models.py`（`RunRule`/`GeoFenceArea`/`RecordDetail`…），哪怕实现糙，也逼着作者先定义字段。我们这里有两处还在"猜字段名"：[policy.rs:22](../src/api/policy.rs#L22) 用 10 个候选名猜必经点，profile 相关还是裸 `Value`。落地：把 policy/fence 响应落成 serde struct，字段缺失立刻在反序列化处报错，而不是静默变空数组。

### 4. 条件拉取：把上次的 updateTime 带回去

参考的 policy body `{"runMode":1,"ruleUpdateTime":0,"geoFenceUpdateTime":0,...}` 和 fence body `{"geoFenceUpdateTime":0}` 与我们的完全一致 ✓，但真机会**回填上次响应的时间戳**。落地：把响应 `timestamp` 存进缓存，下次带上；配合已有的点位 300s 缓存，整体请求量下降，也更接近真机行为。

### 5. 抓包归档：结论必须能回溯到证据

参考套件把每份 HAR 按"场景 + 时间"命名（`…_登录-跑步`、`…_已登录开跑`）并在 README 里指明哪条结论来自哪份抓包。我们的"实测样本"结论散落在注释里（如 [wire.rs:198](../src/track/wire.rs#L198) 的"6 个真人样本跨 9 月记录验证一致"），没有归档的抓包文件可回溯。落地：建 `_captures/`（进 gitignore），每次抓包存一份 + 在注释里写文件名。
